# 项目心得与系统 Bug 总结

> **项目名称**：日常记账理财管理系统  
> **开发周期**：2026-06-04 至 2026-06-06  
> **技术栈**：Vue 3 + FastAPI + MySQL + DeepSeek 大模型  

---

## 一、项目心得

### 1.1 架构设计心得

#### 前后端分离的收益与代价

本项目采用 Vue 3 + FastAPI 的前后端分离架构，这一选择带来了几个显著收益：

- **并行开发**：前端和后端可以独立开发、独立调试。前端通过 Vite 的开发服务器热更新，后端通过 uvicorn 热重载，两者互不干扰。
- **接口契约先行**：在编码前先定义好 API 的路径、请求格式和响应格式，使得前后端对接时几乎没有歧义。实际开发中，9 个核心 API 接口全部一次性对接成功。
- **技术栈灵活性**：前端可以用 Element Plus 组件库快速搭建 UI，后端可以用 Python 生态（SQLAlchemy、bcrypt、openai）快速实现业务逻辑。

代价方面，主要体现在需要同时维护两套运行环境（Node.js + Python），以及跨域（CORS）配置。不过 FastAPI 的 CORSMiddleware 一行配置即可解决。

#### 数据库设计的经验

- **DECIMAL 而非 FLOAT**：金额字段使用 `DECIMAL(10,2)` 而非 `FLOAT`，避免了浮点数精度问题。这是财务系统的底线要求。
- **复合主键的适用场景**：`monthly_budget` 表使用 `(user_id, year_month)` 复合主键，天然保证了"同一用户同一月份仅一条预算记录"的业务约束，比应用层校验更可靠。
- **外键删除策略的权衡**：`bill_record.category_id` 使用默认的 RESTRICT 策略（而非 CASCADE），防止误删分类导致历史账单丢失。这种保守策略在财务系统中是必要的。
- **CHECK 约束的版本兼容性**：MySQL 9.x 对 CHECK 约束的语法要求比 8.x 更严格，列引用需要反引号包裹和额外括号。这提醒我们在写 DDL 时要考虑目标数据库版本。

### 1.2 安全设计心得

#### 密码哈希是底线，不是可选项

项目初期 mock 数据中密码是明文 `123456`，后端登录接口也是明文比对。这在原型阶段可以快速验证功能，但一旦涉及真实用户数据，就必须引入 bcrypt 哈希。修复过程中学到：

- bcrypt 的 `gensalt()` 默认工作因子足够安全，无需手动调参
- 密码哈希后长度固定为 60 字符，`VARCHAR(255)` 的字段长度完全够用
- 迁移已有明文密码时，需要重新生成哈希值并更新数据库

#### 环境变量管理 API Key

大模型的 API Key 绝不能硬编码在代码中。本项目通过 `.env` 文件 + `python-dotenv` 管理，并在 `.gitignore` 中排除 `.env`，同时提供 `.env.example` 模板文件。这样既保证了安全性，又方便其他开发者快速配置。

### 1.3 大模型集成心得

#### Prompt 工程是关键

AI 财务报告的质量高度依赖 Prompt 的设计。开发过程中经历了三次 Prompt 迭代：

1. **初版**：简单的"分析财务数据，给出建议"，生成的报告泛泛而谈。
2. **结构化版**：明确要求报告包含财务概览、分类分析、行为诊断、理财建议等章节，报告质量显著提升。
3. **理论增强版**：引入恩格尔系数、50/30/20 法则、心理账户、锚定效应、损失厌恶、当下偏误等经济学/心理学理论框架，报告不仅有了数据支撑，还有了理论深度。

关键教训：**给大模型的指令越具体，输出质量越高**。比如明确告知"餐饮占比 40%-60% 是正常的，不要批评"，AI 就不会再犯"餐饮占比过高"的低级错误。

#### 缓存机制的必要性

大模型 API 调用有延迟（5-20 秒）和成本。通过 `ai_report` 表缓存已生成的报告，用户再次查看时直接读取数据库，既提升了响应速度，又节省了 API 费用。

### 1.4 前端开发心得

#### 自建 Markdown 渲染的局限性

项目初期使用自写的 `renderMarkdown` 函数做简单的正则替换（标题、粗体、列表），但很快就暴露了问题——表格无法渲染。最终重写了渲染函数，改为按段落块逐块解析，支持了表格、引用块、行内格式等。

**教训**：对于 Markdown 渲染这种通用需求，应该优先考虑使用成熟的库（如 `marked`），自建渲染器容易遗漏边界情况。不过自建也有好处——体积小、可控性强、不引入额外依赖。

#### 状态管理的粒度

项目使用 Pinia 管理用户会话（`session.js`）和预算（`budget.js`）两个全局状态。对于账单数据，选择了在组件内通过 API 获取而非存入全局 store，因为账单数据量大且频繁变更，全局缓存容易导致数据不一致。

### 1.5 模拟数据设计心得

#### 用户画像驱动的数据生成

为了让模拟数据具有测试价值，设计了 5 类用户画像（实习打工族、数码游戏男孩、高收入白领、时尚美妆女孩、节俭学霸），每类画像有不同的收入来源、消费习惯和预算水平。通过 Python 脚本生成 12 个月的账单数据（共 6893 条），包含每日三餐记录和符合画像特征的随机消费。

这种"画像驱动"的数据生成方式比随机生成更有意义，能够验证系统对不同消费模式的分析能力。

## 二、系统 Bug 总结

### 2.1 已修复的 Bug

#### Bug #1：MySQL CHECK 约束语法不兼容

- **严重程度**：高（阻塞数据库初始化）
- **现象**：执行 `initial_schema.sql` 时 MySQL 9.6.0 报语法错误
- **根因**：MySQL 9.x 对 CHECK 约束中列引用的语法要求更严格，需要反引号包裹和额外括号
- **修复**：`CHECK (year_month BETWEEN ...)` → `CHECK ((\`year_month\` BETWEEN ...))`
- **启示**：DDL 脚本应考虑目标数据库版本的语法差异，必要时在注释中标注兼容版本

#### Bug #2：后端明文存储密码

- **严重程度**：高（安全漏洞）
- **现象**：登录接口做明文字符串比对，注册接口直接存明文
- **根因**：开发初期未引入密码哈希方案
- **修复**：引入 bcrypt，注册时 `hashpw()` 加密存储，登录时 `checkpw()` 验证
- **启示**：安全机制应在项目初期就设计好，后期改造涉及数据库迁移，成本更高

#### Bug #3：AI 报告 Markdown 表格未渲染

- **严重程度**：中（影响用户体验）
- **现象**：用户看到的表格是原始 Markdown 文本（竖线、短横线），而非 HTML 表格
- **根因**：自建的 `renderMarkdown` 函数缺少表格解析逻辑，且全局 `\n` → `<br>` 破坏了表格结构
- **修复**：重写渲染函数，按段落块逐块解析，新增 `renderTable()` 和 `processInline()` 辅助函数
- **启示**：自建 Markdown 渲染器需要覆盖表格、列表、引用、代码块等常见语法，建议使用成熟库

### 2.2 已知但未修复的问题

#### 问题 #1：npm 依赖安全漏洞

- **严重程度**：低
- **现象**：`npm install` 报告 5 个漏洞（4 moderate, 1 critical）
- **涉及包**：`whatwg-encoding@3.1.1`、`glob@10.5.0`（均为传递依赖）
- **影响**：仅影响开发/测试环境，不影响生产运行时
- **建议**：定期执行 `npm audit fix`，关注主要依赖的安全公告

#### 问题 #2：SQLAlchemy 2.0 弃用警告

- **严重程度**：低
- **现象**：`MovedIn20Warning: declarative_base() is now available as sqlalchemy.orm.declarative_base()`
- **根因**：使用了旧版导入路径 `sqlalchemy.ext.declarative`
- **影响**：仅为警告，不影响运行
- **建议**：迁移到 `from sqlalchemy.orm import declarative_base`，为未来升级 SQLAlchemy 3.0 做准备

## 三、改进建议

### 3.1 短期改进（可在当前版本实现）

| 改进项 | 优先级 | 说明 |
|--------|--------|------|
| 引入 `marked` 库替代自建 Markdown 渲染 | 中 | 更完善的语法支持，减少边界 bug |

## 四、总结

本项目从零搭建了一个完整的前后端分离记账系统，覆盖了用户认证、账单 CRUD、预算管理、数据可视化和 AI 智能分析五大模块。开发过程中遇到的主要挑战集中在三个方面：

1. **环境兼容性**：MySQL 版本差异、Python 虚拟环境隔离、Node.js 依赖管理等，这些问题虽不涉及业务逻辑，但往往是开发初期最耗时的环节。
2. **安全设计**：密码哈希、API Key 保护、会话隔离等安全机制需要在项目初期就纳入设计，后期改造的成本远高于前期规划。
3. **AI 集成**：大模型的输出质量高度依赖 Prompt 设计，需要结合领域知识（如经济学理论）反复迭代优化，而非一次性完成。

总体而言，系统已具备基本的工程落地价值，可以作为个人财务管理的实用工具，也为后续功能扩展打下了良好的架构基础。
